# 웹앱 개발 전문가 체크리스트

기획 → 디자인 → 프론트엔드 → 백엔드 각 단계에서 전문적으로 고려해야 하는 항목 정리.
ThermaVita Hydro 프로젝트에서 실제로 된 것(✅) / 부분적으로 된 것(⚠️) / 안 된 것(❌)을 함께 표시.

## 1. 기획 (Product Planning)

| 항목 | 설명 | 이 프로젝트 |
|---|---|---|
| 요구사항 정의 | 기능 요구사항 + 비기능 요구사항(성능·보안·접근성) 분리 | ⚠️ 기능 요구사항만 정리(기능정의서), 비기능 요구사항은 거의 안 다룸 |
| 정보구조(IA) | 전체 화면 구조, 내비게이션 체계 | ✅ 여러 차례 검토·수정 |
| 사용자 시나리오 | happy path + 예외 상황(에러, 빈 상태, 권한 없음 등) | ⚠️ 핵심 흐름 위주, 예외 상황은 이번에 지적받고 나서야 보완 중 |
| MVP 범위 정의 | 1차/2차/조건부로 우선순위 구분 | ✅ 화면목록에 1차/2차 구분해둠 |
| **회원 정책** | 본인인증 방식, 탈퇴·휴면계정 처리, 비밀번호 정책 | ❌ 전부 미정/미구현 |
| **법적 요건** | 이용약관, 개인정보처리방침, 데이터 보관기간, 미성년자 정책 | ❌ 화면만 있고 실제 내용은 "준비 중" 플레이스홀더 |
| 콘텐츠 운영 정책 | 관리자 권한 레벨, 콘텐츠 승인 절차 | ⚠️ 관리자 CRUD는 있으나 권한 레벨 구분(다중 관리자) 없음 |
| 성공지표(KPI) | 무엇으로 성공을 측정할지 | ❌ 정의 안 함 |
| 확장성 계획 | 제품 라인 추가, 다국어, 타 시스템 연동 여부 | ⚠️ 데이터 모델은 확장 고려했으나 문서화된 로드맵은 없음 |

## 2. 디자인 (UX/UI)

| 항목 | 설명 | 이 프로젝트 |
|---|---|---|
| 브랜드 아이덴티티 | 컬러·타이포·톤앤매너 | ⚠️ 임시 팔레트, 실제 브랜드 가이드 대기 중 |
| 디자인 시스템 일관성 | 컴포넌트 재사용, 간격/색상 토큰화 | ✅ CSS 변수로 토큰화함 |
| 반응형 디자인 | 모바일/태블릿/데스크톱 대응 | ⚠️ 모바일 우선으로 설계했으나 데스크톱 와이드 레이아웃은 미검증 |
| **접근성(a11y)** | 색상 대비, 키보드 내비게이션, 스크린리더, alt 텍스트 | ❌ 전혀 검토 안 함 |

| 폼 검증 UX | 실시간 피드백, 필드별 에러 표시 | ❌ 방금 지적받은 부분 — 미흡 |
| 마이크로카피 | 버튼 문구, 에러 메시지 톤 | ⚠️ 기능은 있으나 사용자 친화적 문구 다듬기 부족 |
| 다크모드 | 지원 여부 | ❌ 미지원(의도적 스킵) |
| 터치 타겟 크기 | 모바일 44px 이상 권장 | ✅ 버튼 대부분 44px 이상으로 설계 |

## 3. 프론트엔드

| 항목 | 설명 | 이 프로젝트 |
|---|---|---|
| 클라이언트 검증 | required, type, 길이 제한 등 | ⚠️ 기본 HTML 검증만 (required, type=email) |
| **서버 검증** | 클라이언트 우회 대비 서버단 재검증 | ⚠️ 빈 값/일치 여부만 체크, 형식·길이 검증 없음 |
| **폼 상태 보존** | 에러 시 입력값 유지 | ❌ 에러 나면 입력값 전부 날아감 |
| **로딩/중복제출 방지** | 제출 중 버튼 비활성화 | ❌ 없음 |
| 에러 메시지 구체성 | 어느 필드가 문제인지 명시 | ❌ 뭉뚱그린 메시지만 있음 |
| URL 상태 동기화 | 쿼리파라미터로 화면 상태 관리 | ✅ 캘린더 날짜/월, 이력 필터 등 쿼리파라미터로 관리 |
| 딥링크/뒤로가기 | 브라우저 뒤로가기 시 자연스러운 동작 | ✅ 서버 컴포넌트+쿼리파라미터 구조라 기본 지원됨 |
| **민감정보 노출** | 개발용 정보가 프로덕션 화면에 남지 않기 | ❌ 로그인 화면에 데모 계정 비번 그대로 노출 중 |
| 이미지 최적화 | next/image, lazy loading | ❌ 현재 이미지 자체가 플레이스홀더라 미적용 |
| 접근성(aria) | 시맨틱 태그, aria-label | ⚠️ 일부 아이콘 버튼에 aria-label 있으나 전체 검토 안 함 |

## 4. 백엔드

| 항목 | 설명 | 이 프로젝트 |
|---|---|---|
| 비밀번호 해싱 | bcrypt 등 | ✅ bcryptjs 사용 |
| **비밀번호 정책** | 최소 길이/복잡도 | ❌ 없음 |
| **본인인증** | 이메일/SMS 인증 | ❌ 없음 |
| **Rate limiting** | 로그인 시도 제한, 봇 방지 | ❌ 없음 |
| **동시성 처리** | race condition, unique 제약 위반 핸들링 | ❌ 미처리 (동시 가입 시 500 에러 가능) |
| 세션 관리 | 서명된 쿠키, httpOnly | ✅ HMAC 서명 + httpOnly 쿠키 |
| SQL Injection 방지 | ORM 사용 | ✅ Prisma가 기본 방어 |
| 입력 검증(서버) | 타입/길이/형식 | ⚠️ 최소한만 구현 |
| 트랜잭션 관리 | 여러 테이블 쓰기의 원자성 | ⚠️ 대부분 단일 쓰기라 이슈는 적으나 명시적 트랜잭션 처리는 없음 |
| 에러 로깅/모니터링 | 구조화된 로그, 에러 트래킹(Sentry 등) | ❌ 콘솔 로그 수준 |
| 감사 로그(Audit log) | 관리자가 언제 뭘 수정했는지 기록 | ❌ 없음 |
| 시크릿 관리 | .env 분리, 커밋 제외 | ✅ .gitignore로 제외, SESSION_SECRET 별도 관리 |
| 데이터 백업 | 백업 절차 | ✅ 배포가이드에 백업 명령 포함(수동) |
| 권한 검사(authorization) | 특정 데이터에 접근 권한이 실제 소유자인지 확인 | ⚠️ 로그인 여부만 체크, 다른 사용자의 crop ID를 URL로 직접 넣으면 접근되는지 미검증 — **확인 필요** |

## 우선순위 제안

**지금 바로 고쳐야 할 것 (보안/데이터 무결성 관련)**:
1. 비밀번호 최소 길이(8자 이상)
2. 회원가입 동시성 버그(unique 제약 위반 시 친절한 에러 처리)
3. **다른 사용자의 데이터 접근 권한 검사** (예: `/crop/[id]`에서 내 crop이 아닌 남의 crop ID를 넣으면 보이는지 — 아직 미검증, 실제 취약점일 수 있음)
4. 로그인 화면의 데모 계정 정보 노출 제거

**곧 해야 할 것 (UX)**:
5. 폼 에러 시 입력값 보존, 필드별 에러 메시지, 로딩 상태 표시

**부티릭스 결정 필요**:
6. 본인인증 방식(이메일 인증 vs 소셜로그인 vs 생략)
7. 이용약관/개인정보처리방침 실제 내용(법무 검토)

**나중(운영 단계)**:
8. Rate limiting, 감사 로그, 에러 모니터링, 접근성 전면 검토
